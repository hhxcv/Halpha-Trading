# Halpha 开发设计导航

## 权威顺序

以下表示语义的归属与约束关系，不是每项任务必须执行的阅读顺序：

```text
L0 项目边界与最高取舍
→ L1 产品、流程、架构和文档方向
→ L2 领域责任与稳定原则
→ L3 具体对象、接口、状态和失败语义
→ L4 当前工作焦点、版本、配置、事实和结果
→ 实现与测试
```

`docs/L0`–`docs/L4` 当前存在的中文文件就是设计正文，Git 保存历史。实现、测试、索引、登记或流程副本都不能取代正文。

## 当前事实相关时读取 L4

查看 `docs/L4/HALPHA-PLAN-001-current-plan.yaml` 中会影响当前决定的焦点、环境、选择、限制和事实。只有修改计划或无法定位必要上下文时才读完整文件。旧焦点不排除用户新授权的工作；缺失或陈旧事实保持未知。

L4 记录当前选择，不能创造缺失的稳定规则。

## 按问题定位

| 问题 | 首要入口 | 继续读取 |
|---|---|---|
| 当前焦点、版本、配置或验证结果 | 当前 L4 计划 | 其直接引用和实际结果 |
| 稳定语义由谁负责 | 在 L2 标题的“本文档负责”中定位 | 对应 L2、L3 与直接消费者 |
| 对象、接口、状态、错误、幂等或组件使用 | 对应 L3 | 上位 L2、直接依赖和消费者 |
| 开发、测试、新能力或依赖选型、构建或回退 | HALPHA-ENG-001 | HALPHA-ENG-002、相关领域 L3 与 L4 |
| 工作是否值得做 | L0 与 HALPHA-VIS-001 | 必要的 FLOW、ARC 与当前 L4 非目标 |
| 用户流程、停止、接管或恢复 | HALPHA-FLOW-001 | 对应领域 L2/L3 与 L4 |
| 模块、依赖方向、运行角色或环境隔离 | HALPHA-ARC-001 | SYS、ENG 和相关领域文档 |
| 文档内容应放在哪层 | HALPHA-DOC-001 | `write-halpha-docs` |

使用 `rg` 搜索术语、对象和“本文档负责”，再读取相关契约上下文。只沿实际依赖扩展阅读；直接链接足以定位时，不另建需持续同步的导航索引或责任登记。

## 价值与复杂度判断

依次判断：

1. 是否违反 L0 的真实资金边界、用户控制、事实诚实或个人可维护性；
2. 是否改善 L1 定义的用户决策、计划、执行、恢复或复盘价值；
3. 是否符合简单拓扑、成熟组件、唯一事实源和少量运行角色；
4. 是否服务用户授权的当前结果，且与已知事实一致。

把理解、测试、依赖、配置、迁移、运行、升级和回退成本都计入复杂度。前期优先直接实现和直接验证；只有出现不可逆外部影响、真实资金、有效并发、反复故障或明确消费者时才增加管控。

## 仍有疑问时定位缺口

- 用户授权的结果和当前 L4 事实是什么？
- 哪个现有文档拥有受影响语义？
- 哪些成功、拒绝、未知、停止、恢复或接管行为会改变？
- 哪些当前版本或配置会影响实现？
- 本次增加什么价值，删除或引入什么维护成本？

这些问题用于定位影响，不要求每项任务填写预检。常规实现选择自主处理；缺少会实质改变产品含义的决定时，按 [设计不一致处理](design-inconsistency.md) 在现有授权内修订拥有者，或提交需要所有者决定的具体问题。
