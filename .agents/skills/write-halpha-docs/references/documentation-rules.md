# Halpha 文档规则

本参考解释 `HALPHA-DOC-001` 的编辑方法；文档规则与产品语义以当前拥有者正文为准。

## 权威与历史

每个文档编号只在正常目标路径保存一份中文正文；Git commit 保存历史、比较和回退。不建立配对翻译或 proposal、accept、bundle、archive 等规范副本，也不通过状态副本、责任登记或导航索引选择另一份权威。直接链接、就地说明和任务内比较可以辅助阅读，不另建需同步的规则或事实源。

当前状态只从 L4 当前计划或明确事实记录读取。缺少来源、时间或适用范围时保持未知。

## 分层

| 层级 | 只负责 | 不负责 |
|---|---|---|
| L0 | 长期使命、不可突破边界、最高取舍和根本变更条件 | 产品方案、流程、对象、技术、测试和当前状态 |
| L1 | 长期总体文档规则、产品定位、核心路径和总体技术方向 | 字段、完整状态机、供应商、部署和当前工作 |
| L2 | 单一领域的稳定职责、原则、交接和失败边界 | 精确字段、当前组件、当前配置和相邻领域完整流程 |
| L3 | 有实际消费者并需要长期复用的模块、接口、状态、失败和组件使用契约 | 当前工作、精确版本、当前实例和实际结果 |
| L4 | 当前工作焦点、候选后续事项、精确选择、配置、事实、限制和直接结果 | 新增或改写稳定产品规则 |

开发采用连续小步迭代，L0–L4 不使用阶段代号、建设包或阶段完成状态。任务内可以拆分验证步骤；L4 的候选后续事项不是承诺顺序或完成门，记录仅在授权且证据充分时更新。

## 唯一所有者

一项稳定语义只有一个最高拥有层和一个所有者。生产者定义输出；消费者只说明使用条件和缺失结果。相邻文档不得复制完整状态、字段、重试、恢复或授权规则。

当一个对象由横向业务领域拥有时，CAP、DAT、UX、SYS、ENG 等纵向领域只能规定自己的检查或约束，不得重新定义该对象生命周期。跨域顺序只由确有必要的协调者描述一次。

## 内容门槛

只保留会改变以下至少一项的内容：用户结果、责任归属、允许行为、失败结果、停止与接管、实现边界或当前决定。

新增需要长期维护的概念、记录、状态、流程、组件或治理检查时，说明当前消费者与实际价值，比较更小方案。删除后不改变当前行为或判断的内容应删除；普通措辞和局部结构调整不需另写论证。

当前实现已经由代码、配置、锁文件、数据库迁移或 Git 直接拥有时，L4 引用其路径和当前结论，不复制完整 schema、版本清单或摘要。只有人工决策必须独立读取时才在 L4 保留少量值。

## 文件与语言

- 规范文件使用 `HALPHA-<类型>-<序号>-<英文短标题>.zh-CN.md`。
- 只使用中文规范；必要代码标识、外部标准和组件名称可以保留英文。
- 除 L0 外，文档头至少包含文档编号、层级、语言、上位、负责和不负责范围。
- L0 至少包含文档编号、层级、语言、适用范围和权威范围。
- 不要求显式语义锚点、固定章节模板、定义/要求/依据分类或机器配套文件。
- L4 YAML 必须包含文档编号、层级、时间和当前事实的适用范围。

## 编辑与验证

按影响读取目标含义及必要上下文，修改拥有者和真正受影响的直接引用。语义变更读取完整相关契约，总体或跨域变更再扩展阅读上位全文；不机械遍历各层。

复核差异及其上下文是否正确表达主体、输入未知、失败与结束。涉及文件拆分、整体改写或总体规则时复读修改文件全文。执行 [验证方法](validation.md) 的适用检查；无需为每次编辑重复目标声明、建立表单或更新无事实变化的 L4。

评审分别说明文本内部是否一致、层级和所有权是否正确。结论不以篇幅、检查数量或形式完整度为依据。
